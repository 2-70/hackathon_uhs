## 시작할 때 공유할 API 예시

서버 작업과 함께 API 요청·응답 초안을 `docs/api-contract.md`에 기록하고 팀 채팅에 공유한다. 의류 ID, 기기 ID, 코스 값은 개발용 예시를 써서 앱과 서버를 동시에 시작한다. 시연용 상품과 세탁기 모델의 공식 정보는 실제 데이터 검증 전에 준비한다.

| 연결 지점 | 함께 정할 항목 |
|---|---|
| 이진영 ↔ 유상진 · 의류 분석 | 사진 업로드 형식, 의류·라벨 구분, 제품 일치 상태, 필드별 출처, 확인 필요 상태와 오류 형식 |
| 이진영 ↔ 이우진 · 옷장과 기기 | 의류·세탁기 ID, 사용자 입력의 저장 형식, 앱 재실행 후 등록 기기를 불러오는 방법 |
| 이진영 ↔ 이우진 · 세탁 계획 | 의류 ID와 기기 ID를 전달하는 형식, 그룹과 제외·보류 목록, 코스·온도·탈수, 분리 사유, 건조 조건, 최신 입력을 구분하는 방법 |
| 유상진 ↔ 이우진 · 시드 데이터 | 상품과 기기 모델을 식별하는 값, 실제 지원 코스·설정 조합, 출처 URL, 검증 상태, 로더가 읽을 형식 |

이진영과 유상진이 채팅에 남긴 의견을 확인하고 API를 연결하기 전에 예시에 반영한다. 이진영은 개발용 응답을 붙이고, 유상진은 AI 라우터와 시드 파일을 작성한다. 해석이 다른 부분이 생기면 관련 담당자끼리 짧게 맞춘다.

## P0 작업

- [ ] **서버 뼈대** · FastAPI, Neon 연결, Alembic, 의존성 파일을 구성한다. 유상진에게 AI 라우터 등록 위치, DB 세션을 가져오는 방법, 사용할 수 있는 상품 조회 경로를 전달한다.
- [ ] **영속 저장과 시드 로더** · 옷장과 사용자 세탁기, 출처가 있는 상품 및 기기 정보의 저장 구조를 준비한다. 유상진이 제공하는 검증 데이터를 읽어 반복 실행해도 중복 생성되지 않게 한다.
- [ ] **옷장과 모델 API** · `/api/wardrobe`의 목록·저장·수정·삭제, `/api/machines`와 모델별 코스 조회, `/api/user-machines` 등록을 구현한다. 정확한 모델과 실제 지원 조합을 반환한다.
- [ ] **세탁 그룹 계산** · `POST /api/plans`에서 최대 10벌의 필수 세탁 조건을 검증하고, 같은 코스·설정으로 세탁할 수 있는 조합 중 그룹 수가 가장 적은 계획을 계산한다. 손세탁·기계세탁 불가·정보 부족 의류는 별도로 반환한다. 그룹, 설정, 분리 이유와 의류별 확인된 건조 방법을 앱에 넘긴다.
- [ ] **현재 설정 검증** · `POST /api/settings/validate`에서 실제 기기 모델의 지원 범위와 각 의류의 필수 조건을 적용해 `적합`, `수정 필요`, `판단 불가` 및 이유를 반환한다. 추천 코스와 다른 설정도 필수 조건을 충족하면 적합으로 처리한다.
- [ ] **통합 환경** · AI 라우터를 연결하고 Neon DB 마이그레이션과 시드를 실행한다. Android 실기기에서 접근할 수 있는 API 주소와 실행 방법을 이진영에게 전달한다. Gemini 키와 DB 접속 정보는 서버 환경변수에서 읽는다.

## 시간과 검증

- **1–8시간** · 서버 뼈대, DB, 옷장·기기 API를 먼저 열어 실기기 연결을 준비한다. 그룹 엔진은 합의한 예시 데이터로 병렬 개발한다.
- **8–12시간** · AI 라우터와 첫 세탁 계획 API를 연결한다. 공식 데이터가 준비되기 전에는 테스트 DB의 개발용 시드로 요청과 계산을 검증한다.
- **12시간 전후** · 이진영, 유상진과 함께 테스트 사진과 기기 데이터로 분석 결과 저장부터 계획 조회까지 연결한다. 연결이 끊기는 지점부터 수정한다.
- **12–20시간** · 조건이 충돌하는 여러 벌, 정보가 부족한 의류, 등록되지 않은 모델, 잘못된 온도·탈수 조합을 검증한다. 의류가 중복 배정되거나 누락되는지 확인한다.
- **마지막 4시간** · 실기기에서 옷 추가·제거 후 재계산과 오래된 응답 처리, 앱 재실행 후 옷장 조회, 건조 안내까지 함께 확인한다. README에 실행 방법과 검증 결과를 남긴다.
