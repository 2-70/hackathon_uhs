# WashWise 백엔드 1단계 제품 요구명세서

**핵심 개념**
앱이 옷과 기기를 등록하면 서버가 데이터를 DB에 저장하고, 앱을 다시 열었을 때 같은 목록을 돌려줍니다.
모바일·AI 담당자가 동시에 개발할 수 있도록 어떤 주소로 어떤 데이터를 주고받을지 먼저 합의합니다.

| 항목 | 내용 |
| --- | --- |
| 상태 | 승인 완료 · 백엔드 1단계 구현 완료 |
| 담당 | 이우진 |
| 일정 | 24시간 해커톤의 첫 번째 구현 단계 |
| 이번 승인 단위 | API 계약, 서버·DB 기반, 옷장·기기 기본 API, 검증 시드 로더, 앱 연동 검증 |

## 1. 개발 목적과 사용자

- 세탁할 옷과 사용할 기기를 재실행 후에도 선택할 수 있도록 등록 정보를 보존합니다.
- 데모 사용자는 옷장에 의류를 추가하고, 본인이 사용할 세탁 기기를 등록한 뒤 다시 조회합니다.
- 이진영 님은 모바일 화면에서 사용할 요청·응답 예시를 받아 서버 구현과 병행해 작업합니다.
- 유상진 님은 공용 DB 세션과 모델을 통해 AI 처리 결과와 출처를 일관된 형식으로 전달합니다.

## 2. 범위와 우선순위

| 우선순위 | 요구사항 | 완료 결과 |
| --- | --- | --- |
| P0 | API 계약 합의안 작성 | 필수 필드, 자료형, 오류, 예시, 구현 상태와 담당자를 문서화합니다. |
| P0 | 서버·DB 시작 경로 마련 | FastAPI가 시작하고 PostgreSQL에 Alembic 초기 스키마를 적용할 수 있습니다. |
| P0 | 옷장 등록·조회·수정·삭제 | 저장된 의류를 같은 사용자가 다시 조회할 수 있습니다. |
| P0 | 기기 등록·조회 | 저장된 기기와 등록 근거를 같은 사용자가 다시 조회할 수 있습니다. |
| P0 | 검증 시드 로딩 | 확인된 원본을 가져오고 반복 실행해도 중복되지 않습니다. |
| P0 | 앱 연결 기반 검증 | 모바일 담당자가 사용할 서버 주소, 예시 요청, 성공·오류 응답을 제공합니다. |
| P1 | 실제 모바일 연동 확인 | 모바일 빌드가 준비되면 등록·재실행·조회를 함께 확인합니다. |

세탁 조합 최적화, 기기 설정 적합성 판정, AI 분석과 제품 검색의 실제 처리, 모바일 화면 개발은 후속 또는 다른 담당자의 작업입니다.
이번 단계에서는 해당 호출의 입출력 초안을 작성하고 미구현 기능을 문서에 표시합니다.

이우진 님은 공용 앱에서 AI 라우터를 등록할 위치와 경로 접두사를 문서화합니다.
공용 DB 세션은 요청 단위로 제공하며, 예외 시 롤백하고 종료 시 반환합니다.
모델과 세션의 실제 import 경로, 쓰기 트랜잭션의 책임 주체를 계약에 명시합니다. AI 담당 파일은 각 소유자가 수정합니다.

## 4. 서버와 데이터 요구사항

- Python과 FastAPI로 요청 검증 및 OpenAPI 명세를 제공하고 SQLAlchemy로 데이터를 읽고 씁니다.
- PostgreSQL을 기준으로 Alembic 마이그레이션을 관리하며, 실제 연동 대상은 Neon입니다.
- DB 접속 문자열과 외부 서비스 키는 서버 환경변수에 둡니다. `.env.example`에는 변수 이름과 가짜 예시 값만 둡니다.
- 앱에는 호출할 서버 주소를 제공합니다. DB 접속 정보와 외부 서비스 비밀 키는 서버에서만 읽습니다.
- 계정 인증은 미정입니다. P0에서는 개발 모드에서만 동작하는 단일 데모 사용자 식별 방식을 제안합니다.
- 데모 모드를 명시적으로 선택하고 서버가 소유자를 지정합니다. 옷장·기기 조회도 같은 소유자 조건을 사용합니다.

| 저장 대상 | 보존할 정보와 출처 | 확인 상태 처리 |
| --- | --- | --- |
| 옷장 의류 | 소유자, 의류 식별자, 사용자 입력 또는 라벨 분석에서 온 세탁 정보 | 값의 출처와 사용자 확인 여부를 구분하고 모르는 값은 비워 둡니다. |
| 공용 제품 및 세탁 정보 | 제품 식별자, 브랜드·제품명, 확인된 필드별 세탁 지침·출처를 저장합니다. | 공식 정보와 사용자 소유 의류 기록을 구분합니다. |
| 공용 기기 모델 | 제조사·모델 식별 정보, 출처 문서, 확인된 코스와 지원 설정 조합 | 공식 근거와 확인 범위를 추적합니다. 근거가 없는 조합은 추가하지 않습니다. |
| 사용자 등록 기기 | 소유자, 기기 종류, 사용자가 입력한 명칭·설정, 연결 가능한 공용 모델 ID | 수동 입력은 해당 등록 기기에 귀속시키고 공용 모델을 덮어쓰지 않습니다. |
| 검증 시드 | 유상진 님이 제공한 고유 식별값, 원본 출처, 확인 상태, 모델·코스 데이터 | 로더가 필수 필드를 검증하고 어느 레코드가 실패했는지 표시합니다. |

온도와 탈수 강도 사이에 제약이 있으면 코스별로 실제 지원하는 조합을 한 단위로 저장합니다.
예를 들어 확인된 두 조합이 ‘30도·약’, ‘40도·중’이면 ‘30도·중’을 자동 생성하지 않습니다.
필드별 출처는 실물라벨·공식제품정보·의류사진추정·사용자입력으로 구분합니다. 확인 상태 값은 확인·미확인을 초안으로 제안하며, 시드 필수 키와 함께 팀에서 확정합니다.

## 5. API 계약 초안

아래 표는 호출 목적을 기준으로 정리했습니다. 경로와 필드 이름은 팀 명세에 맞춰 확정합니다.

| 호출 | 요청과 성공 응답에 담을 내용 | 구현 범위 |
| --- | --- | --- |
| 서버 상태 조회 | 요청 후 서버 가동 상태를 반환합니다. DB 연결 확인 결과는 별도로 검증합니다. | 이우진, 이번 단계 |
| POST /api/wardrobe | 의류 정보와 출처를 받아 생성 ID와 저장된 값을 반환합니다. | 이우진, 이번 단계 |
| GET /api/wardrobe | 현재 사용자의 의류 목록을 반환합니다. 비어 있으면 빈 배열을 반환합니다. | 이우진, 이번 단계 |
| PATCH /api/wardrobe/{id}, DELETE /api/wardrobe/{id} | 본인이 등록한 의류를 수정하거나 삭제하고 조회 결과에 반영합니다. | 이우진, 이번 단계 |
| GET /api/machines, GET /api/machines/{id}/courses | 공용 모델 목록과 해당 모델의 코스별 지원 설정 조합을 조회합니다. | 이우진, 이번 단계 |
| POST /api/user-machines | 기기 종류, 공용 모델 참조 또는 수동 입력을 받아 등록 ID를 반환합니다. | 이우진, 이번 단계 |
| GET /api/user-machines | 현재 사용자의 기기와 모델 참조·수동 입력 상태를 반환합니다. | 이우진, 이번 단계 제안 |
| POST /api/analyze | 이미지와 요청 식별값을 받아 추출 정보, 확인이 필요한 항목, 식별값을 반환하는 예시를 둡니다. | 유상진, 이번 단계는 계약 |
| POST /api/products/match | 제품 검색 입력에 대해 동일제품확인·유사제품후보·검색결과없음·조회오류를 구분하고 출처를 담은 응답을 예시합니다. | AI 검색은 유상진, 공용 DB 접점은 이우진 |
| GET /api/products/{id}/care | 제품별 세탁 정보, 필드별 출처와 확인 상태를 반환합니다. | 유상진, 이번 단계는 계약 |
| POST /api/plans | 선택한 의류·기기 식별값에 대해 세탁 묶음과 권장 설정을 제시하는 응답을 예시합니다. | 이우진, 엔진은 후속 |
| POST /api/settings/validate | 선택 기기·코스·설정 조합에 대해 적합·수정필요·판단불가 중 하나와 그 근거를 반환하는 예시를 둡니다. | 이우진, 판정은 후속 |

입력 변경 후 늦게 도착한 이전 응답을 앱이 구분하도록 요청 식별자 또는 입력 버전을 그대로 돌려주는 방식을 제안합니다.
예시로 두 번째 요청이 먼저 완료되어도 앱은 현재 입력과 일치하는 응답만 표시합니다. 최종 필드명과 적용 대상은 팀 합의 사항입니다.

### 오류 응답

- 공통 형식은 `error.code`(앱 분기용), `error.message`(안내 문구), 선택 항목인 `error.details`(필드별 원인)를 제안합니다.
- 예시 응답은 `{"error":{"code":"INVALID_INPUT","message":"기기 종류를 입력해 주세요.","details":{"field":"type"}}}`입니다.
- 필수 입력 누락·형식 오류는 422, 존재하지 않는 참조는 404를 제안합니다. 등록 성공은 201, 목록 조회 성공은 200입니다.
- 서버 오류는 내부 원인을 로그에 기록하고 앱에는 공통 안내를 반환합니다. 응답에 키나 DB 접속 문자열이 노출되지 않게 합니다.

## 6. 실행 순서와 의존성

1. 기존 명세의 엔드포인트와 역할을 대조해 계약 초안을 정리합니다. 등록·목록·오류 응답 예시를 먼저 공유 가능한 상태로 작성합니다.
2. 공용 서버 진입점, 설정, SQLAlchemy 세션과 모델을 만들고 빈 PostgreSQL DB에 초기 마이그레이션을 적용합니다.
3. 옷장과 등록 기기 API를 구현하고 같은 사용자로 재조회했을 때 저장값이 유지되는지 확인합니다.
4. 검증 제품·제품별 세탁 지침과 기기·코스 시드의 입력 규격을 맞추고 안정적인 고유 키와 DB 유일성 제약으로 중복을 방지합니다. 오류 발생 시 해당 로딩 작업을 롤백합니다.
5. 모바일 담당자가 사용할 주소·예시를 정리하고 실제 연결 여부와 사용한 환경을 기록합니다.

Neon 자격 정보, 원본 검증 시드, 모바일 빌드의 준비 시점은 각각 외부 의존성입니다.
시드가 도착하기 전에는 테스트 전용 데이터로 로더를 검증하고 데모용 공식 데이터와 구분합니다.
미정 사항은 데모 사용자 처리, 공식 출처 및 확인 상태의 필드, 시드 고유 키, 입력 버전 형식, API 최종 경로입니다.

## 7. 완료 기준과 검증 증거

| 검사 | 통과 기준 |
| --- | --- |
| 옷장 변경 | 수정한 내용이 조회되고 삭제한 항목이 목록에서 제외되는지 확인합니다. |
| 공용 제품 조회 기반 | 시드 제품을 ID로 다시 읽어 필드별 세탁 지침·출처가 유지되는지 DB에서 검증합니다. |
| 공용 기기 조회 | 모델을 선택하면 해당 모델의 코스와 설정만 조회되는지 확인합니다. |
| 초기 기동 | 문서의 명령으로 서버를 시작하고 빈 PostgreSQL DB에 마이그레이션을 적용합니다. |
| 옷장·기기 | 각각 등록한 후 새 요청으로 조회해 ID와 저장값을 대조하며, 서버 재시작 후에도 같은 레코드가 조회됩니다. |
| 빈 목록·잘못된 입력 | 신규 사용자에게 빈 목록을 반환하고 필수값 누락 시 공통 오류 코드와 메시지를 반환합니다. |
| 출처·설정 조합 | 수동 입력이 공용 모델을 바꾸지 않으며, 저장 전후 출력에 실제 확인된 조합만 남는지 비교합니다. |
| 반복 로딩 | 같은 시드를 두 번 로딩해 제품·세탁 지침·모델·코스·설정 조합 수가 늘지 않으며 오류 입력은 부분 저장되지 않습니다. |
| 계약 일치 | 실제 구현된 경로의 상태 코드와 응답 예시를 서버 응답과 대조합니다. 후속 경로에는 구현 상태를 명시합니다. |
| 앱 복원 | API 조회 검증과 실제 앱 재실행 검증을 나누어 기록합니다. 실제 빌드가 준비되면 동일한 등록값을 확인합니다. |
| 환경별 확인 | 로컬 PostgreSQL 및 실제 Neon 결과를 각각 기록합니다. 자격 정보가 없으면 Neon 검증은 미완으로 표시합니다. |

## 8. 승인 및 완료 문서

현재 **승인 완료**이며, 승인 범위의 구현과 로컬 검증·완료 문서화를 진행했습니다.
커밋, 원격 푸시, 외부 메시지 발송은 이번 작업 범위에 포함하지 않습니다.
