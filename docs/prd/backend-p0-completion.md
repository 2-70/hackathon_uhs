# WashWise 이우진 담당 P0 완료 제품 요구명세서

## 핵심 개념

사용자가 선택한 옷마다 확인된 세탁 제한을 읽고, 등록한 **정확한 세탁기 모델에서 실제로 지원하는 설정 조합**과 비교합니다. 서버는 안전하다고 추측하지 않고, 근거가 충분한 옷만 최소 횟수의 기계세탁 그룹으로 묶습니다. 손세탁·물세탁 금지·정보 부족 의류는 별도 목록으로 반환하며, 사용자가 실제 세탁기에 입력한 설정도 같은 규칙으로 독립 검증합니다.

| 항목 | 내용 |
| --- | --- |
| 상태 | 사용자 지시로 검토·보완 후 구현 승인 완료 (2026-11-11) |
| 담당 | 이우진 |
| 기준 문서 | `WASHWISE_SPEC.md`, `docs/tasks/이우진.md` |
| 선행 완료 | 백엔드 기반, Neon, 옷장 CRUD, 기기 모델·코스 조회, 사용자 기기 등록·조회, 시드 로더 |
| 구현 세션 | 기존 구현 채팅의 현재 모델 설정 유지 |
| 승인 단위 | 아래 P0 데이터·계획·설정검증·AI/모바일 통합·검증 전체 |

## 1. 개발 목적

- 최대 10벌의 의류를 필수 관리 조건과 실제 세탁기 지원 조합에 따라 분류합니다.
- 가능한 기계세탁 그룹 중 세탁 횟수가 최소인 계획을 계산합니다.
- 사용자가 실제 기기에서 선택한 설정이 추천값과 달라도 조건을 충족하면 적합으로 판정합니다.
- 확인되지 않은 값, 서로 충돌하는 출처, 수치로 비교할 수 없는 기기 설정은 임의의 안전 기본값으로 바꾸지 않습니다.
- AI 분석·공식 상품·사용자 입력·실물 라벨의 출처와 확인 상태를 필드별로 보존합니다.
- 기존 Neon 의류, 공식 모델, 사용자 등록 기기와 API 호출 형식을 깨지 않는 추가형 migration을 사용합니다.
- 모바일이 늦게 도착한 과거 응답을 버릴 수 있도록 요청 식별값과 실제 계산 입력 스냅샷을 반환합니다.

## 5. 데이터 구조와 migration

### 5.1 migration 순서

1. 원격 AI 제공물의 `0002_analysis_integration`을 먼저 적용합니다.
2. 새 `0003_backend_p0_planning`을 추가형 migration으로 적용합니다.
3. 기존 열 삭제·이름 변경·타입 축소를 하지 않습니다.
4. 새 열은 기존 행을 위해 nullable 또는 안전한 서버 생성값으로 시작합니다.
5. 기존 `wardrobe_items`, `machine_models`, `machine_courses`, `machine_course_settings`, `user_machines`의 ID와 외래 키를 유지합니다.

### 5.2 의류 기본 정보 확장

`wardrobe_items`에 다음 선택 필드를 추가합니다.

- 제품 참조: 브랜드, 제품명, 품번, 공용 제품 ID, 공식 URL
- 사진 참조: 모바일 또는 비공개 저장소가 관리하는 불투명 참조값
- 세탁: `care_wash_method`, 최대 온도, 허용 세탁 강도, 최대 탈수 RPM 또는 탈수 단계
- 분리: 색상군, 이염 위험, 단독세탁 여부
- 건조: 건조기 허용, 최대 건조 열, 자연건조 방식, 그늘건조 여부
- 용량: 의류 무게 g. 확인되지 않으면 `null`

AI `0002`가 추가하는 `care_wash_method`, `care_gentle`, `care_tumble_dry_allowed`는 유지합니다. `care_gentle`은 기존 모바일 하위호환 필드로 두고 새 세탁 강도 필드와 동기화합니다.

### 5.3 필드별 출처·확인 상태

새 `wardrobe_care_fields` 테이블을 사용합니다.

| 필드 | 설명 |
| --- | --- |
| `wardrobe_item_id`, `field_name` | 의류와 관리 필드의 복합 고유 키 |
| `value_json` | 문자열·숫자·불리언 값을 원형대로 보존 |
| `source_type` | `physical_label`, `official_product_information`, `photo_inference`, `user_input` |
| `source_reference` | 공식 URL, 라벨 참조, 분석 요청 식별값 등 |
| `evidence` | 원문 또는 확인 근거 |
| `knowledge_status` | `confirmed`, `unconfirmed`, `needs_confirmation`, `conflict`, `not_applicable` |
| `conflicting_values` | 출처가 다른 값과 근거의 배열 |
| `updated_at` | 입력 스냅샷과 재계산에 사용하는 시각 |

기존 의류는 item 수준의 `source_type`, `verification_status`와 기존 값으로 읽을 수 있게 fallback을 제공합니다. 새 쓰기부터 필드별 근거를 함께 저장합니다. 공식 정보와 실물 라벨이 다르면 한 값을 조용히 덮어쓰지 않고 `conflict`와 두 근거를 반환합니다.

### 5.4 기기 모델과 실제 설정 조합

- `machine_models`: 용량 kg, 출시연도, 용량 근거 URL·확인 상태
- `machine_course_settings`: 원문 온도 설정명, 섭씨 값, 세탁 강도, 탈수 단계, RPM, 기본 조합 여부, 매뉴얼 페이지·근거
- 설정 한 행은 실제로 함께 선택 가능한 한 조합입니다.
- 이름만 확인된 `Warm`을 임의로 40℃로, `High`를 임의 RPM으로 바꾸지 않습니다.
- 수치 비교가 필요한데 수치 근거가 없으면 해당 비교의 상태를 `unknown`으로 둡니다.
- 수동 기기는 해당 `user_machines.manual_input`에 확인된 코스·조합·용량을 저장하며 공용 모델을 수정하지 않습니다.

## 6. 옷장 API 하위호환

- 기존 `POST/PATCH /api/wardrobe` 본문은 그대로 허용합니다.
- 새 선택 필드 `product_reference`, `image_reference`, `care_fields`를 추가합니다.
- 기존 scalar 필드와 `care_fields`가 함께 오면 값·근거가 일치하는지 검증합니다.
- 같은 요청에서 scalar와 `care_fields`에 서로 다른 값을 보내면 422 `CONFLICTING_INPUT`으로 거부합니다. 공식 자료와 라벨 등 서로 다른 출처의 실제 충돌은 `conflict` 상태와 두 근거를 저장하며 임의 우선순위를 적용하지 않습니다.
- 응답은 기존 필드를 유지하고 필드별 근거·확인 상태를 추가합니다.
- 알 수 없는 값은 `null`, 확인 필요는 `needs_confirmation`으로 구분합니다.

## 7. `POST /api/plans`

### 7.1 요청

```json
{
  "request_id": "plan-20261111-001",
  "input_version": 4,
  "wardrobe_item_ids": ["의류 UUID 1", "의류 UUID 2"],
  "user_machine_id": "사용자 기기 UUID",
  "expected_item_versions": {
    "의류 UUID 1": "updated_at ISO 문자열",
    "의류 UUID 2": "updated_at ISO 문자열"
  }
}
```

검증 규칙:

- 1~10개, 중복 ID 금지
- 모든 의류와 사용자 기기가 현재 소유자에게 속해야 함
- 누락 ID, 다른 사용자 ID, 모델이 없는 기기, 지원 조합이 없는 기기를 구분
- `expected_item_versions`가 제공되고 현재 값과 다르면 409 `STALE_INPUT`
- 예상 버전을 제공할 경우 요청의 모든 의류 ID를 정확히 포함해야 합니다. 일부 의류만 검사하고 전체 버전 검증 성공으로 처리하지 않습니다.

### 7.2 의류 분류

각 의류는 정확히 한 곳에만 배정합니다.

- `groups`: 기계세탁 가능한 그룹. 한 벌 그룹도 허용
- `hand_wash_items`: 손세탁 전용
- `machine_wash_prohibited_items`: 물세탁·기계세탁 불가
- `pending_confirmation_items`: 핵심 조건 부족 또는 출처 충돌
- `unsupported_items`: 의류 조건은 확인됐지만 해당 모델에 가능한 조합이 없음

기계세탁 핵심 조건은 세탁 방법, 최대 온도, 세탁 강도, 색상·이염·단독세탁 조건입니다. 최대 탈수 제한이 확인된 경우 반드시 적용합니다. 탈수 제한이 공식 자료에 명시되지 않은 것인지 아직 확인하지 못한 것인지 필드 상태로 구분합니다.

분류 우선순위는 확인된 물세탁·기계세탁 금지, 확인된 손세탁 전용, 핵심 정보 부족·충돌, 실제 지원 조합 유무, 그룹 계산 순서입니다. 모델 설정의 비교 근거가 부족한 경우는 `unsupported_items`가 아니라 `pending_confirmation_items`에 필요한 확인 항목을 표시합니다. 필요한 비교가 모두 가능하고 실제 호환 조합이 없을 때만 미지원으로 분류합니다.

### 7.3 설정 호환 규칙

설정 조합은 다음을 모두 만족해야 합니다.

- 선택한 사용자 기기의 정확한 공용 모델 또는 사용자 확인 수동 프로필에 속함
- 조합의 확인 상태가 `confirmed`
- 설정 온도가 모든 의류의 최대 온도 이하임
- 설정 세탁 강도가 모든 의류의 허용 강도 이하임
- 탈수 제한이 있으면 RPM 또는 단계가 허용 범위 안임
- 단독세탁 의류는 그룹 크기가 1임
- 밝은색·어두운색과 이염 위험 조건이 충돌하지 않음
- 용량과 모든 의류 무게가 확인되면 합계가 기기 용량 이하임

비교에 필요한 수치가 기기 또는 의류에서 확인되지 않으면 추정하지 않습니다. 해당 의류를 확인 보류하거나 비교 항목을 판단 불가로 표시합니다.

### 7.4 부분집합 DP

1. 기계세탁 후보를 비트마스크로 표현합니다.
2. 모든 비어 있지 않은 부분집합에 대해 분리 규칙과 공통 지원 설정을 계산합니다.
3. 가능한 부분집합만 후보 그룹으로 보관합니다.
4. 아직 배정되지 않은 가장 작은 인덱스 의류를 포함하는 후보만 전이해 같은 분할의 순열 중복을 줄입니다.
5. `dp[mask]`에 해당 의류를 덮는 최소 그룹 수와 분할을 저장합니다.
6. 그룹 수가 같으면 정렬된 의류 ID·코스 키·설정 키의 사전식 순서로 동점을 결정합니다.

설정 선택은 호환 조합 중 확인된 기본 조합을 우선하고, 그다음 코스 키·설정 키의 안정적인 순서를 사용합니다. 모든 선택은 이미 의류 제한을 통과한 조합에서만 이뤄집니다.

### 7.5 응답

- 요청의 `request_id`, `input_version`을 그대로 반환
- 서버가 실제 읽은 의류 ID·`updated_at`, 사용자 기기·모델, 설정 조합 내용을 정렬해 만든 `input_fingerprint`
- 그룹별 의류 ID, 코스 ID·키, 설정 ID와 전체 실제 설정값
- 기계세탁 횟수, 추천 이유, 분리 이유, 근거와 출처
- 각 의류의 확인된 건조 방법과 확인 필요 필드
- 용량 검증 상태: `verified`, `not_verified`, `exceeded`
- 모든 입력 의류가 정확히 한 결과 위치에 있다는 invariant 검사 결과

## 8. `POST /api/settings/validate`

### 8.1 요청

```json
{
  "request_id": "setting-20261111-001",
  "input_version": 5,
  "wardrobe_item_ids": ["의류 UUID 1"],
  "user_machine_id": "사용자 기기 UUID",
  "course_id": "코스 UUID",
  "setting_id": null,
  "actual_setting": {
    "temperature_celsius": 40,
    "temperature_setting": null,
    "wash_strength": "normal",
    "spin_rpm": 1000,
    "spin_level": null
  }
}
```

`setting_id`는 앱에서 저장된 조합을 선택할 때 사용합니다. 사용자가 실제 기기에 입력한 미지원 조합도 검증할 수 있도록 `actual_setting`을 별도로 허용합니다. 둘 다 오면 일치 여부를 확인합니다.

### 8.2 판정

- `suitable`: 실제 모델 지원 조합이며 모든 확인된 의류 조건을 충족
- `needs_change`: 모델 미지원 조합 또는 한 개 이상의 확인된 조건 위반
- `unknown`: 모델·입력·의류 조건이 부족하거나 충돌해 판단 불가

추천값과 같은지만 비교하지 않습니다. 추천과 달라도 조건을 모두 만족하면 `suitable`입니다.

확인된 위반이 하나라도 있으면 다른 미확인 항목이 함께 있어도 `needs_change`를 반환하고 미확인 항목도 별도 표시합니다. 확인된 위반 없이 필수 비교가 남아 있으면 `unknown`, 모든 필수 비교를 통과한 경우에만 `suitable`을 반환합니다. 탈수 단계는 모델별 비교 근거가 있을 때만 순서를 비교하며 서로 다른 기기의 단계명을 전역 RPM으로 바꾸지 않습니다.

응답에는 위반 필드, 의류별 이유, 모델 미지원 이유, 가능한 대체 설정 목록, 최신 입력 식별 정보를 포함합니다. 대체 설정은 실제 모델에 저장된 조합 중 모든 의류 조건을 만족하는 것만 반환합니다.

## 9. 최신 입력과 오래된 응답 처리

- 앱이 모든 계획·설정검증 요청에 `request_id`와 증가하는 `input_version`을 보냅니다.
- 서버는 두 값을 바꾸지 않고 반환합니다.
- 서버는 실제 DB의 `updated_at`과 설정 조합을 포함한 `input_fingerprint`를 반환합니다.
- fingerprint에는 필드별 근거·충돌 상태, 수동 기기 프로필, 모델·코스·설정·용량의 실제 계산값도 포함합니다. 단순 ID만 해시하지 않으며 비밀정보는 포함하지 않습니다.
- 앱은 현재 화면의 `request_id`와 `input_version`이 일치하는 응답만 적용합니다.
- 옷 추가·제거·수정, 기기 변경 후에는 이전 요청을 취소하거나 결과를 폐기하고 새 버전으로 요청합니다.
- 서버는 제공된 예상 버전이 현재 DB와 다르면 409 `STALE_INPUT`을 반환합니다.
- 서버가 응답 순서를 제어할 수 없으므로 화면 덮어쓰기 방지는 모바일의 최종 책임임을 계약에 명시합니다.

## 10. AI 제공물 통합

1. 원격 `d0af266`의 AI 소유 파일을 내용 변경 없이 가져옵니다.
2. 공용 `0002_analysis_integration`과 모델·시드 로더 변경을 검토해 적용합니다.
3. AI 라우터가 이미 `/api` prefix를 가질 때 추가 prefix를 붙이지 않습니다.
4. `get_catalog` 의존성을 Neon 기반 `get_db_catalog`로 교체합니다.
5. 상품 API가 JSON 파일 fallback이 아니라 실제 DB 행을 사용하는 통합 테스트를 유지합니다.
6. `httpx`, Pillow, `python-multipart` 런타임 의존성을 공용 환경에 추가합니다.
7. Gemini 키가 없을 때 상품 조회는 가능하고 이미지 분석은 명시적 설정 오류를 반환해야 합니다.

AI 분석의 `request_id`·`input_version` echo와 필드 충돌 전체 보존은 AI 소유 인터페이스 보완 사항입니다. 공용 계약과 인계 문서에 요구 형식을 기록하고, 해당 변경이 원격 제공물에 없으면 실제 AI 최신입력 통합은 미완료로 표시합니다.

## 11. 모바일 연결 기준

현재 모바일은 옷장·기기·AI는 실제 API를 사용하지만 계획·설정검증은 로컬 mock입니다. 모바일 담당자에게 다음 변경을 전달합니다.

- 옷 추가·제거·수정 때 `input_version` 증가

`EXPO_PUBLIC_API_URL`은 휴대폰과 같은 네트워크의 PC LAN IP를 사용합니다. `127.0.0.1`은 휴대폰 자신이므로 실기기 주소로 사용하지 않습니다. Windows 방화벽 허용과 `/health` 접근을 먼저 확인합니다.

## 13. 공식 시드와 출처 검증

- 공식 URL과 근거 문구를 다시 확인하고 확인한 범위만 `confirmed`로 유지합니다.
- 상품 공식 페이지에 온도·건조 정보가 없으면 `null`과 `needs_confirmation`을 유지합니다.
- LG `WM4000HWA`의 설정명은 설명서 원문으로 유지하고 섭씨·RPM을 추정하지 않습니다.
- 시드 로더는 기존 예시 JSON과 새 공식 JSON을 모두 읽습니다.
- 같은 시드를 두 번 적재해 제품·관리필드·모델·코스·설정 수와 안정 ID가 늘지 않아야 합니다.
- 입력 문서 전체를 먼저 검증하고 하나의 트랜잭션으로 저장합니다.
- 잘못된 설정 한 건이 있으면 해당 실행의 변경 전체를 롤백합니다.

## 14. 테스트 요구사항

- 기존 의류·기기·사용자기기 행을 넣은 뒤 `0003` 적용하고 ID·값 유지

- 알려진 용량·무게 초과와 용량 미검증
- 탐욕법보다 DP가 더 적은 그룹을 찾는 반례
- 각 의류 중복·누락 없음
- 입력 순서가 달라도 동일한 동점 결과

### 설정 검증

- 추천과 다르지만 적합한 설정
- 미지원 온도·탈수·강도 조합
- 의류 최대 온도·강도·탈수 위반
- 부분 입력과 판단 불가
- 가능한 대체 설정만 반환

- AI 상품 매칭이 Neon 행을 사용
