- 모바일 `drum.tsx`는 계획·설정검증에 아직 `src/mock.ts`를 사용합니다.
- 실제 Android 전체 사용자 흐름과 오래된 응답 폐기는 모바일 담당자 반영 후 확인해야 합니다.

## 4. 포트폴리오용 정리

### 프로젝트 한 줄 요약 및 본인의 기여도

의류별 검증 근거와 실제 세탁기 지원 조합을 기반으로 최대 10벌의 최소 세탁 계획과 실제 설정 안전성을 계산하는 WashWise 백엔드를 설계·구현했습니다.

이우진 님의 기여는 공용 API 계약, SQLAlchemy 데이터 확장, Alembic migration, 필드별 출처·충돌 모델, 계획·설정검증 규칙 엔진, 부분집합 DP, 최신 입력 fingerprint, Neon 적용·HTTP 검증, 시드 통합과 회귀 테스트입니다. AI 전용 파일과 모바일 소스는 담당자 제공물을 그대로 유지했습니다.

### 가장 까다로웠던 기술적 도전과 성장 포인트

가장 까다로운 문제는 “모르는 값”과 “조건을 위반하는 값”을 구분하는 일이었습니다. 공식 설명서의 `Warm`, `High`를 임의 숫자로 바꾸면 계획은 만들어지지만 근거 없는 안전 판정이 됩니다. 이를 해결하기 위해 값마다 `knowledge_status`와 출처를 저장하고, 비교 근거가 없으면 미지원이 아니라 확인 보류로 분류했습니다. 설정 검증도 확인된 위반이 있으면 `needs_change`, 위반 없이 비교만 남으면 `unknown`이 되도록 우선순위를 고정했습니다.

두 번째 도전은 최소 세탁 횟수와 결정론을 동시에 보장하는 것이었습니다. 가능한 의류 부분집합마다 실제 공통 설정을 먼저 확인한 뒤 비트마스크 DP로 최소 그룹 수를 계산하고, 동률에서는 의류 ID·코스 키·설정 키 순서로 선택했습니다. 탐욕법이 3회를 선택하지만 DP가 2회를 찾는 반례와 입력 순서 독립성을 테스트로 증명했습니다.

마지막으로 기존 Neon 사용자 데이터를 보존하면서 스키마를 확장했습니다. 로컬에서 빈 DB·기존 행 보존·downgrade를 검증한 후 실제 Neon에 추가형 migration을 적용했고, 전후 행 수와 대표 ID, `alembic check`, HTTP 응답을 확인했습니다. 이를 통해 기능 구현뿐 아니라 데이터 migration과 운영 검증까지 하나의 완료 조건으로 다루는 경험을 쌓았습니다.

#### 가장 까다로웠던 기술적 도전과 성장 포인트

가장 큰 도전은 대량 PDF 처리와 Neon 연결 수명을 분리하는 일이었습니다. 초기에는 긴 PDF를 읽는 동안 하나의 DB 세션을 유지해 유휴 연결이 종료됐습니다. 문서 ID·URL만 메모리로 분리하고 다운로드·추출 뒤 배치마다 새 세션으로 저장하도록 바꿨으며, 끊긴 연결은 멱등 배치 단위로 재시도했습니다. 이를 통해 네트워크 작업과 트랜잭션의 수명을 같게 두면 안 된다는 운영 설계 원칙을 익혔습니다.

두 번째 도전은 “공식 문서”와 “바로 추천해도 되는 데이터”를 구분하는 일이었습니다. 제목·목차·다국어 본문·문자 깨짐이 키워드에 걸리는 문제를 표본 검수로 발견했고, 대체문자·목차 점선·다국어 우세 문장을 필터링한 뒤 영향 문서만 선택 재처리했습니다. 최종 3,976행도 모두 `needs_review`로 남겨 공식 출처와 자동 추출 정확도를 별개의 상태로 관리했습니다.
