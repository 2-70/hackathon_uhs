## 4. 포트폴리오용 정리

### 프로젝트 한 줄 요약 및 본인의 기여도

의류와 세탁 기기 정보를 재실행 후에도 복원하고, 검증된 실제 기기 설정 조합만 제공하는 WashWise 백엔드 기반을 설계·구현했습니다.

이우진 님의 실제 기여 범위는 공용 API 계약, FastAPI 서버 구조, SQLAlchemy 데이터 모델, Alembic 초기 migration, 옷장 CRUD, 공용 기기 조회, 사용자 기기 등록·복원, 멱등성 시드 로더, 공통 오류 처리, 실행·검증 문서입니다. AI 전용 경로와 모바일 코드는 수정하지 않았습니다.

### Tech Stack Rationale

| 기술 | 채택 이유 |
| --- | --- |
| FastAPI | Pydantic 입력 검증과 OpenAPI 문서를 자동 제공해 모바일·AI 담당자와 계약을 빠르게 공유할 수 있습니다. |
| SQLAlchemy 2 | SQLite와 PostgreSQL을 같은 모델·쿼리 구조로 사용하면서 트랜잭션과 관계를 명확히 관리할 수 있습니다. |
| Alembic | 빈 DB부터 동일한 스키마를 재현하고 이후 변경 이력을 단계적으로 관리할 수 있습니다. |
| Neon PostgreSQL | 해커톤에서 관리 부담이 적은 서버리스 PostgreSQL을 사용하면서 관계·유일성 제약을 유지할 수 있습니다. |
| Pydantic Settings | 비밀정보를 코드와 분리하고 `.env`·배포 환경변수에서 같은 설정 이름을 사용할 수 있습니다. |
| pytest | 저장·재조회·중복 방지·롤백처럼 사람이 놓치기 쉬운 데이터 동작을 반복 검증할 수 있습니다. |
| uv | Python 런타임·가상환경·잠금 파일·의존성 설치를 하나의 도구로 재현할 수 있습니다. |

### 가장 까다로웠던 기술적 도전과 성장 포인트

가장 까다로운 부분은 세탁기 코스의 온도와 탈수 강도를 각각 저장하면 확인되지 않은 교차 조합이 생길 수 있다는 점이었습니다. 이를 해결하기 위해 설정을 한 행의 조합으로 저장하고, `setting_key`와 DB 유일성 제약으로 같은 조합만 멱등성 있게 갱신했습니다. 그 결과 `30도·약`, `40도·중`만 확인된 경우 `30도·중`을 임의로 만들지 않는 데이터 구조를 확보했습니다.

또한 시드 파일의 모든 중복 키와 필수 필드를 쓰기 전에 검증하고, 제품과 기기 적재를 하나의 트랜잭션으로 묶었습니다. 이 과정에서 데이터 신뢰성은 단순 입력 검증뿐 아니라 안정 키, 유일성 제약, 트랜잭션 경계를 함께 설계해야 한다는 점을 학습할 수 있습니다.

검증 환경에서는 Windows 샌드박스가 Python 이벤트 루프의 socketpair를 제한하는 문제를 앱 오류와 분리했습니다. 최소 asyncio 코드와 스레드 스택으로 환경 문제를 확인하고, 가능한 동기식 DB·라우터 검증을 끝낸 뒤 HTTP 검증만 미완료로 정확히 남겼습니다. 이는 실패를 숨기지 않고 검증 가능한 범위를 분리하는 실무적 디버깅 경험으로 정리할 수 있습니다.
