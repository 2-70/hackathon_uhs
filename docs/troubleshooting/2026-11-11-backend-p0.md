# 트러블슈팅 보고서: 백엔드 P0 계획·설정검증

## 1. 옷장 라우터 패치 문맥 불일치

### 발생한 오류 및 원인 파악

- 첫 패치가 `selectinload` import가 이미 존재한다고 가정했지만 실제 파일에는 없어서 적용 도구가 문맥을 찾지 못했습니다.
- 패치는 적용 전 중단되어 파일 손상은 없었습니다.

### 해결 방법 제시 (수정된 코드 포함)

실제 파일 상단을 다시 확인하고 import와 공통 조회 함수를 작은 패치로 추가했습니다.

```python
from sqlalchemy.orm import selectinload

def _wardrobe_statement(owner_id: str):
    return (
        select(WardrobeItem)
        .options(selectinload(WardrobeItem.care_fields))
        .where(WardrobeItem.owner_id == owner_id)
    )
```

### 재발 방지 대책

- 공용 파일 수정 전 대상 줄을 다시 읽고 현재 import·함수 문맥을 기준으로 작은 패치를 적용합니다.
- 팀원이 동시에 수정할 수 있는 공용 파일은 큰 범위 교체를 피합니다.

## 2. Windows 샌드박스의 uv 캐시 접근 거부

### 발생한 오류 및 원인 파악

- `uv sync`, Ruff, pytest 실행 시 샌드박스 임시 프로필의 uv 캐시에 파일을 저장하지 못해 `os error 5`가 발생했습니다.
- 프로젝트 코드나 의존성 정의가 아니라 실행 환경의 파일 권한 문제였습니다.

### 해결 방법 제시 (수정된 코드 포함)

코드는 바꾸지 않고 승인된 프로젝트 범위에서 명령을 샌드박스 밖으로 다시 실행했습니다.

```powershell
uv sync --extra dev
uv run ruff check backend migrations
uv run pytest
```

### 재발 방지 대책

- 같은 `uv` 캐시 오류가 확인되면 소스 우회를 만들지 않고 필요한 명령만 제한적으로 권한 승인 후 재실행합니다.
- 오류 로그에 접속 문자열이나 API 키를 출력하지 않습니다.

## 3. HTTP 오류 처리 변수 위치

### 발생한 오류 및 원인 파악

- AI 라우터의 구조화된 `HTTPException.detail`을 보존하는 변경에서 `detail` 변수를 `ApiError` 핸들러에 잘못 삽입했습니다.
- Ruff가 미사용 변수와 HTTP 핸들러의 미정의 변수를 동시에 발견했습니다.

### 해결 방법 제시 (수정된 코드 포함)

```python
@app.exception_handler(HTTPException)
async def handle_http_error(_: Request, exc: HTTPException) -> JSONResponse:
    detail = exc.detail if isinstance(exc.detail, dict) else {}
    return JSONResponse(
        status_code=exc.status_code,
        content={
            "error": {
                "code": detail.get("code", "HTTP_ERROR"),
                "message": detail.get("message", str(exc.detail)),
                "details": None,
            }
        },
    )
```

### 재발 방지 대책

- 예외 핸들러 수정 직후 Ruff를 실행해 변수 범위와 미사용 값을 확인합니다.
- 같은 형태의 `return JSONResponse`가 여러 곳에 있을 때 함수 이름까지 포함한 문맥으로 패치합니다.

## 4. 비기본 설정 테스트의 SQLAlchemy 관계 캐시

### 발생한 오류 및 원인 파악

- 테스트 하나에서 첫 설정을 조회한 같은 세션에 두 번째 설정을 추가했습니다.
- 실제 서버는 요청마다 세션이 새로 열리지만 테스트 fixture는 한 세션을 재사용해 이미 로드된 관계 목록이 이전 값으로 남았습니다.

### 해결 방법 제시 (수정된 코드 포함)

```python
db_session.add(alternate)
db_session.commit()
db_session.expire_all()
```

### 재발 방지 대책

- 같은 세션에서 관계 데이터를 추가한 뒤 새 HTTP 요청 상황을 재현할 때 `expire_all()`로 DB 값을 다시 읽습니다.
- 실패 단언문에는 HTTP 상태와 오류 본문을 함께 표시해 계산 오류와 fixture 오류를 구분합니다.

## 5. PowerShell HTTP 검증의 단일 배열 직렬화

### 발생한 오류 및 원인 파악

- 단일 원소 API 배열을 중첩 배열처럼 다뤄 `user_machine_id`가 문자열 대신 배열 또는 null로 직렬화됐습니다.
- 서버는 계약대로 422 `INVALID_INPUT`을 반환했습니다.

### 해결 방법 제시 (수정된 코드 포함)

응답 원문을 명시적으로 JSON 변환하고 ID를 문자열로 지정했습니다. 현재 데모 소유자에게 사용자 기기가 없다는 것도 별도로 확인해, 검증 전용 행을 생성한 뒤 정확한 ID만 삭제했습니다.

```powershell
$items = (Invoke-WebRequest -Uri "$base/api/wardrobe").Content | ConvertFrom-Json
$item = @($items)[0]
$payload = @{
    wardrobe_item_ids = @([string]$item.id)
    user_machine_id = [string]$machine.id
} | ConvertTo-Json
```

### 재발 방지 대책

- PowerShell HTTP 스크립트에 `$ErrorActionPreference='Stop'`을 사용합니다.
- JSON 배열·ID 자료형을 요청 직전에 명시적으로 고정합니다.
- 실제 Neon 검증용 행은 고유 ID를 기록하고 `finally`에서 그 ID만 삭제합니다.

## 6. 공식 이름형 설정의 안정 키 확장 위험

### 발생한 오류 및 원인 파악

- 새 `wash_strength`를 `setting_key`에 추가하면서 기존 AI 시드의 `[temperature_setting, spin_rpm]` 키가 3개 값 배열로 바뀔 가능성을 발견했습니다.
- 그대로 적재하면 같은 공식 설정이 다른 키로 인식되어 중복될 수 있었습니다.

### 해결 방법 제시 (수정된 코드 포함)

```python
extra_values = [self.temperature_setting, self.spin_rpm]
if self.wash_strength is not None:
    extra_values.append(self.wash_strength)
```

- 기존 시드에 강도 값이 없으면 이전 두 값 키를 그대로 유지합니다.
- 공식 시드를 두 번 적재해 설정 수가 3건으로 유지되는 자동 테스트와 Neon 검증을 추가했습니다.

### 재발 방지 대책

- 안정 키 생성 규칙은 새 nullable 필드가 비어 있을 때 기존 결과가 완전히 같아야 합니다.
- 공식 시드 변경 전후 키 집합과 행 수를 자동 테스트로 비교합니다.
